| BSL-05 | OPEN | A per-minute token counter admits all waiting streams at once when it refills or its key changes, and APIM counts a stream only when it finishes. Overshoot is about one burst of a person's parallel requests (12 Sonnet streams: about $1.92). Run 3 (2026-10-24, power-of-two ceiling, no reservation) ended $0.18 over a $52.11 budget, so the burst is not certain to occur. A per-request reservation (not published) was rejected in code review on 2026-10-24: with an expression `increment-count`, APIM postpones the count to the end of the outbound pipeline, so simultaneous requests are all admitted ([rate-limit-by-key](https://learn.microsoft.com/azure/api-management/rate-limit-by-key-policy)); and charging `max_tokens` per request caps request count for people under budget. A per-person concurrency cap does not bound it either (BSL-06). Remaining options, each a separate decision: a smaller pacing window or soft-limit percentage, accepting about one burst of parallel requests as the overshoot (run 3: $0.18), or a request-path spend counter (ADR 0035 option 3). |
| BSL-06 | RESOLVED | APIM `limit-concurrency` around `forward-request buffer-response="false"` releases its slot when the response headers arrive, not when a stream ends. Measured 2026-10-24 on a temporary, key-protected probe API on the lab Standard v2 APIM (`max-count` 2, Haiku): two streams returned headers at 2.3 s and ended at 6.0 s; a third request sent at 4 s returned 200. Control: five simultaneous non-streamed requests returned 200, 429, 429, 429, 200, so the limit is enforced while a response is pending. Policy reference: [limit-concurrency](https://learn.microsoft.com/azure/api-management/limit-concurrency-policy). A per-person concurrency cap therefore limits how many streams start at once, not how many run, and does not bound BSL-05. The probe API and its subscription were deleted (path returns 404). Evidence: session `files\pseudo\bsl06`. |

| DR-13 | RESOLVED | DR-08: the 16 Region B HTTP 504s (2026-10-25T19:21:04Z-19:48:42Z) were caused by the drill itself. At 19:20Z the drill pointed Region B pool member 0 at an unreachable address (`10.80.9.250`) to simulate a primary backend outage. Before that change, member 0 served 6 of 6 calls through the private path (19:17:43Z-19:20:03Z); every 504 went to the injected address. The breaker (failureCount 1, interval PT1M, tripDuration PT2M, `Timeout` included) then sent traffic to the Central US fallback (15 HTTP 200s) and re-probed member 0 once per trip, each probe timing out after about 21 s. The fault was still in place on 2026-10-26 and was removed at 2026-10-26T05:22:29Z from the saved original. Remaining design note: during a sustained primary-backend outage, one request per trip interval receives a 504; a longer trip duration or a pool retry would reduce that. Source: live `ApiManagementGatewayLogs`, saved backend definitions, [APIM backends](https://learn.microsoft.com/azure/api-management/backends). Follow-up (a breaker edit does not queue a revision), investigated 2026-10-26: a project's routing revision is the integer `failover.revision`; pool and member entity IDs are built from project ID and revision only (`src/contracts/project-routing.ts:45-51`), and the breaker is copied from the registry into the plan only when the publisher reads `routing/pending` (`admin/src/backend-routing.ts:131`). The revision moves only when the ordered fallback list changes (`admin/src/backend-routing.ts:94`), and a project is pending only while `active.revision` differs from it (`admin/src/backend-routing.ts:109`). `PUT backends/{id}` saves the registry entry and touches no project (`admin/src/v3.ts:436-459`). A breaker-only edit therefore leaves every verified project `verified` on APIM entities that keep the old breaker. Resolved 2026-10-26 for projects with failover on: a breaker change now moves each verified project whose pool includes the backend to a new pending revision, with an ETag-guarded write, change record and audit line per project (`failoverAfterBreakerChange` in `admin/src/backend-routing.ts`, `requeueAfterBreakerChange` in `admin/src/v3.ts`; tests in `admin/tests/backend-routing.test.ts`). Still open: a `disabled_with_pool` project switched back on with the same fallback list reuses its old pool and breaker, and a URL-only edit queues no revision. No live publication of a breaker-triggered revision has been run. |

| APIM-ZR-03 | RESOLVED | One unit is allowed with zone redundancy on Standard v2 and Premium v2: units are spread across zones best-effort and a single unit's compute is distributed to two zones. Microsoft recommends at least two units so that a zone outage does not reduce gateway capacity. Source: [Reliability in API Management (Standard v2)](https://learn.microsoft.com/azure/reliability/reliability-api-management?pivots=standard-v2), retrieved 2026-10-26. The configuration readers therefore print a warning, not a refusal, for fewer than two units. |
